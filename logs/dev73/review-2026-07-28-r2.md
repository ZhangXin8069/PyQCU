## 1. 新发现 — 致命 Bug (🔴🔴)

### 1.0 🔴🔴 CRITICAL: CG solver `_init()` 内存泄漏 — 覆盖 LatticeSet 预分配缓冲区

**文件**: `cpp/cuda/qcu/include/lattice_wilson_cg.h:40-54`  
**严重程度**: 🔴🔴 致命

```cpp
// LatticeWilsonCg::_init() 重新分配 LatticeSet::init() 已分配过的缓冲区:
cudaMallocAsync(&set_ptr->device_vec0, lat_4dim_SC * sizeof(...), stream); // 泄漏!
cudaMallocAsync(&set_ptr->device_vec1, lat_4dim_SC * sizeof(...), stream); // 泄漏!
cudaMallocAsync(&set_ptr->device_vec2, lat_4dim_SC * sizeof(...), stream); // 泄漏!
cudaMallocAsync(&set_ptr->device_vals, _vals_size_ * sizeof(...), stream); // 泄漏!
```

`LatticeSet::init()` 在 `_SET_PLAN_ >= _SET_PLAN1_` 时已分配这些缓冲区。`LatticeWilsonCg::_init()` 用新指针覆盖旧指针，但**旧指针丢失，旧 GPU 内存永不释放**。这是确定性 GPU 内存泄漏。

对比：`LatticeWilsonBistabCg::_init()` 和 `LatticeCloverBistabCg::_init()` 正确复用了 `LatticeSet` 的分配，没有此问题。

**修复**: 删除 `LatticeWilsonCg::_init()` 中这 4 行 `cudaMallocAsync`，直接复用 `set_ptr` 的现有缓冲区。

### 1.0b 🔴🔴 CRITICAL: Multigrid 求解器硬编码 `MPI_FLOAT` 破坏 double 精度

**文件**: `cpp/cuda/qcu/include/lattice_clover_multigrid.h:204, 440`  
**严重程度**: 🔴🔴 致命 — double 精度下产生错误结果

```cpp
// dot_mpi() — 总是用 MPI_FLOAT, 即使 T=double:
T global = host_tmp.real();
MPI_Allreduce(MPI_IN_PLACE, &global, 1, MPI_FLOAT, MPI_SUM, MPI_COMM_WORLD);

// fine_norm2() — 硬编码 float:
float g = host_tmp.real();
MPI_Allreduce(MPI_IN_PLACE, &g, 1, MPI_FLOAT, MPI_SUM, MPI_COMM_WORLD);
return (T)g;  // double → float → double 精度丢失!
```

所有其他 solver（Wilson/Clover BiStabCG, Wilson CG）都使用模板派发 `_MPI_Allreduce<T>`（正确 dispatch `MPI_DOUBLE` vs `MPI_FLOAT`），但 multigrid solver 绕过了此抽象直接硬编码 `MPI_FLOAT`。

**影响**: 任何使用 `_LAT_C128_` (complex128/double) 精度运行 multigrid 求解器的计算，所有 MPI 向量点积的 double 值被截断为 float。**收敛性判断和最终结果均为错误值。**

**修复**: 使用 `MPI_Datatype mpi_type = std::is_same<T, double>::value ? MPI_DOUBLE : MPI_FLOAT;` 或调用已有模板 `_MPI_Allreduce<T>`。

### 1.0c 🔴🔴 CRITICAL: `check_su3` — float32 精度下 `allclose` 默认 `atol=1e-8` 过严，SU(3) 验证始终失败

**文件**: `pyqcu/lattice/__init__.py:132-143`  
**严重程度**: 🔴🔴 致命 — SU(3) 正确性检查功能完全失效

```python
_torch.allclose(UH_U, eye, rtol=tol)   # tol=1e-3, atol defaults to 1e-8!
```

对于 complex64 (float32 精度)，矩阵乘法 `U^H @ U` 的非对角元素产生的数值误差约 $6\times 10^{-8} \sim 8\times 10^{-8}$，超过了默认 `atol=1e-8`。这意味着 **`check_su3` 返回 True 的情况极少，即使 gauge field 是正确的 SU(3) 矩阵**。

**实验验证**: 用 `generate_gauge_field(seed=42, sigma=0.1)` 生成 gauge field，`check_su3(U, tol=1e-3)` 返回 `False`；加上 `atol=1e-3` 后返回 `True`。

**影响**: 所有依赖 `check_su3` 的测试和代码可能错误地报告 SU(3) 违反，增加不必要的调试时间。同时如果开发者习惯了 check_su3 返回 False，真正的 SU(3) 违规就会被忽略。

**修复**: 所有 `_torch.allclose` 调用添加 `atol=tol`:
```python
unitary_ok = _torch.allclose(UH_U, eye, rtol=tol, atol=tol)
det_ok = _torch.allclose(det_U, torch.ones_like(det_U), rtol=tol, atol=tol)
```

### 1.0d 🔴 HIGH: `stout_smear` NPU 路径 `f1` 的 parity 符号翻转缺失实部取反

**文件**: `pyqcu/smear/_stout.py:157`  
**严重程度**: 🔴 严重 — NPU 上 stout smearing 结果错误

```python
# 标准 CUDA/CPU 路径 (line 161):
f1[parity] = -f1[parity].conj()   # 正确: 取共轭后实部虚部都取反

# NPU 路径 (line 157):
f1.imag[parity] = -f1.imag[parity]   # 错误: 只翻转虚部，实部不变！
```

对于 `f1 = 2+3j`，标准路径给出 `-2+3j`（共轭→取反→虚部恢复），NPU 路径给出 `2-3j`（仅虚部取反）。**`f0` 和 `f2` 的 parity 处理是正确的**（`conj()` 等效于 `imag[parity] = -imag[parity]`），但 `f1` 多了额外取负号 `-f1.conj()`，NPU 路径遗漏了实部取反。

**修复**: 
```python
f1.real[parity] = -f1.real[parity]
f1.imag[parity] = -f1.imag[parity]
```

### 1.1 🔴 `stout_smear` 数值稳定性：无除零和 arccos 域外保护

**文件**: `pyqcu/smear/_stout.py:131-136`  
**严重程度**: 🔴 严重 — 极端 gauge 配置下产生 NaN

```python
c0 = einsum("ab...,bc...,ca...->...", Q, Q, Q).real / 3   # 可能 ≈ 0
c1 = einsum("ab...,ba...->...", Q, Q).real / 2               # 可能 ≈ 0
c0_max = 2 * (c1 / 3) ** (3 / 2)                             # c1=0 → c0_max=0
theta = torch.arccos(c0 / c0_max)                             # 0/0 → NaN!
```

**触发条件**:
- 当 Q 矩阵接近零（gauge links 接近 identity）时，c1 ≈ 0，导致 c0_max = 0
- `c0 / c0_max` 产生 `0/0 = NaN`
- 浮点舍入可能导致 `c0/c0_max > 1.0`，`arccos(>1)` = NaN

**实际触发概率**: 在多步 smearing 后 gauge 场变得更平滑，Q 可能趋于零。对于恒等 gauge 场（U=I），确定性触发。

**修复**: 添加 `c1` 极小值的 guard：
```python
eps = 1e-15
c1 = torch.clamp(c1, min=eps)
c0_max = 2 * (c1 / 3) ** (3 / 2)
# 同时 clamp arccos 参数
ratio = torch.clamp(c0 / c0_max, -1.0 + eps, 1.0 - eps)
theta = torch.arccos(ratio)
```

### 1.2 🔴 C++ BiCGStab `_init`/`__init` 分配的 GPU 内存未释放

**文件**: `cpp/cuda/qcu/include/lattice_clover_bistabcg.h:38-95`  
**严重程度**: 🔴 严重 — GPU 内存泄漏

```cpp
void _init() {
    cudaMallocAsync(&b__o, lat_4dim_SC * sizeof(...), stream);  // 分配
    cudaMallocAsync(&r, lat_4dim_SC * sizeof(...), stream);      // 分配
    cudaMallocAsync(&r_tilde, ...);                               // 分配
    cudaMallocAsync(&p, ...);                                     // 分配
    cudaMallocAsync(&v, ...);                                     // 分配
    cudaMallocAsync(&s, ...);                                     // 分配
    cudaMallocAsync(&t, ...);                                     // 分配
    // 没有对应的 _end() 来 cudaFreeAsync！
}

void __init() {
    cudaMallocAsync(&x_o, ...);   // 分配（无对应释放）
    cudaMallocAsync(&ans_e, ...); // 分配（无对应释放）
    cudaMallocAsync(&ans_o, ...); // 分配（无对应释放）
    cudaMallocAsync(&b_e, ...);   // 分配（无对应释放）
    cudaMallocAsync(&b_o, ...);   // 分配（无对应释放）
    // 没有对应的 __end() 来释放！
}
```

`_init()` 分配 7 个 buffer（共约 `7 * lat_4dim * 12 * sizeof(T)` 字节），`__init()` 分配 5 个 buffer。这些 buffer 不与 `LatticeSet` 关联，`applyEndQcu` 不会释放它们。

**影响**: 每次 BiCGStab 求解调用泄漏约 `12 * lat_4dim * 12 * sizeof(complex64) = 12 * 32^4 * 8 = ~3.8 GB` 对于 $32^4$ 晶格（12 个 buffer）。实际泄漏量取决于 `if_input` 标志 —— `_init` 始终分配 7 个，`__init` 仅在 `if_input==0` 时分配 5 个。

**修复**: 添加 `_end()` 和 `__end()` 函数调用 `cudaFreeAsync`，并在求解完成后调用。

### 1.3 🔴 C++ Clover BiStabCG solver `host_vals` 未在 host 和 device 间同步

**文件**: `cpp/cuda/qcu/include/lattice_clover_bistabcg.h:28, 131-164`  
**严重程度**: 🔴 严重 — 潜在收敛失败/死循环

```cpp
LatticeComplex<T> host_vals[_vals_size_];  // line 28: host 端数组
// ...
// line 131-164: 在求解循环中
give_1custom<T><<<1, 1, 0, stream>>>(device_vals, _rho_, T(1.0), T(0.0));
// 设置 device_vals 但从未同步到 host_vals
// ...
for (int i = 0; i < max_iter; i++) {
    // 从 device_vals 读取标量
    bistabcg_give_1beta<T><<<1, 1, 0, stream>>>(device_vals);
    // ...
    if (host_vals[_diff2_tmp_].real < host_vals[_norm2_tmp_].real * tol * tol) {
        break;  // ← host_vals 可能包含过期数据！
    }
```

收敛检查在 line ~152 使用 `host_vals`，但这些值写入了 `device_vals`（GPU 内存），从未通过 `cudaMemcpy` 复制回 `host_vals`。收敛判断可能永远基于初始值，导致求解器永不收敛或过早退出。

**修复**: 在收敛检查前添加：
```cpp
cudaMemcpyAsync(host_vals, device_vals, sizeof(LatticeComplex<T>) * _vals_size_,
                cudaMemcpyDeviceToHost, stream);
cudaStreamSynchronize(stream);
```

### 1.4 C++ Clover BiStabCG `bistabcg_give_dest_o` 使用 `kappa²` — ✅ **PASS（设计决策）**

**文件**: `cpp/cuda/qcu/src/bistabcg.cu:84`  
**审查结论**: 不是 bug。`kappa²` 对应 odd-preconditioned 系统 $M_{\text{prec}} = M_{oo} - \kappa^2 M_{oe} M_{ee}^{-1} M_{eo}$ 的解恢复公式。标准 Clover-Wilson 的 parity preconditioning 在偶数位解恢复中确实需要 `kappa²` 因子。已添加代码注释和数学推导说明。

### 1.5 🔴 C++ 晶格尺寸非 `_BLOCK_SIZE_` 整数倍时遗漏边界 site

**文件**: `cpp/cuda/qcu/include/lattice_set.h:140-163` (grid 计算); 所有 `.cu`/`.h` 中的 kernel launch sites  
**严重程度**: 🔴 严重 — 静默丢失计算结果

```cpp
gridDim_2dim[_XY_] = lat_2dim[_XY_] / _BLOCK_SIZE_;   // 整数除法截断!
gridDim = lat_4dim / _BLOCK_SIZE_;                     // 整数除法截断!
```

当 `lat_4dim` 不能被 `_BLOCK_SIZE_` (16) 整除时，余数 site 被跳过。例如 `lat_4dim = 17`，`gridDim = 1`，只处理 16/17 个 site。

对比：multigrid kernels (`multigrid.cu:12-13`) 已正确实现 `if (global_idx >= total_output) return;` bounds check，但 **dslash、pick_up_u、solver kernels 全部缺少此保护**。

**修复**: 所有 gridDim 计算用 `(total + _BLOCK_SIZE_ - 1) / _BLOCK_SIZE_`，kernel 内添加 `if (idx >= volume) return;`。

### 2.4 🟡 `restrict_npu` 中的 `_fine_vec` reshape 路径有维度 8 限制

**文件**: `pyqcu/tools/_multigrid.py:186-218`

`local_orthogonalize_npu`、`restrict_npu`、`prolong_npu` 中通过多次 reshape/permute 绕过了 NPU 的 8 维限制。这些手动维度重组逻辑与标准路径（使用 10 维 einsum）不同，存在索引错误的可能。应添加与标准路径的对比测试。

### 2.5 🟡 `tools._io` MPI 串行路径 `comm.scatter` 可能在大晶格失败

### 2.6 `wilson_dslash_inside` `lat_t=1` 时 t 方向内部检测错误 — ✅ **PASS（设计决策）**

### 2.8 `_WILSON_AND_LAPLACIAN_TEST_SINGLE_IN_MULTI_ = 1` — ✅ **PASS（设计决策）**

**文件**: `cpp/cuda/qcu/include/define.h:220`

### 2.9 🟡 BiCGStab 无 breakdown 检测

**文件**: `pyqcu/solver/_bistabcg.py:38-47`, `pyqcu/solver/_multigrid.py:351-359`  
**严重程度**: 🟡 中等

BiCGStab 算法没有检查 breakdown 条件：
- `rho = vdot(r_tilde, r)` 接近 0 时，`alpha = rho / vdot(r_tilde, v)` 产生 0 或 NaN
- `vdot(r_tilde, v)` = 0 时直接除零
- `t = 0` 时 `omega = vdot(t, s) / vdot(t, t)` 除零

NaN 值传播后 `r_norm < _tol` 永远为 False（NaN 与任何值比较都是 False），导致循环跑满 `max_iter` 而静默返回错误解。

**修复**: 添加 `if abs(rho) < 1e-30:` 等 breakdown 检测并 raise RuntimeError。

### 2.10 🟡 `_linalg.py` `vdot` 中 Allreduce 前后仍有冗余 Barrier

**文件**: `pyqcu/tools/_linalg.py:21, 26`  
**严重程度**: 🟡 中等

首轮优化移除了 `_operator.py` 和 `_clover.py` 中的冗余 Barrier，但 `_linalg.py` 的 `vdot` 函数中的 `comm.Barrier()` 在 `Allreduce` 前后仍然存在。`Allreduce` 本身就阻塞同步，Barrier 是多余的。每次 BiCGStab 迭代都调用 `vdot` 5 次（rho, rho_prev, alpha, omega, norm），即每迭代 5 次冗余全局同步。

**修复**: 移除 line 21 和 line 26 的 `comm.Barrier()`。

## 4. 新发现 — 文档与健壮性

### 4.1 📝 粗网格算子构造假设 coarsening=2

**文件**: `pyqcu/dslash/_operator.py:153-217`  
**严重程度**: 📝 文档缺失

Galerkin 投影中的 even/odd site 分离（`start=0` / `start=1` with `step=2`）仅当每个方向 coarse/fine 比 = 2 时正确。对于非标准 coarsening（如 4×4×4×4 → 1×1×1×1），分解不完全。标准用法是 `mg_grid_size = [2,2,2,2]`，所以实践中无问题，但应文档化此假设。

### 4.2 📝 `_lat_4dim_` float-to-int 转换精度限制

**文件**: `cpp/cuda/qcu/src/bistabcg.cu:36`, `cg.cu` 多处  
**严重程度**: 📝 文档

```cpp
int _ = int(((LatticeComplex<T> *)device_vals)[_lat_4dim_]._data.x);
```

`_lat_4dim_` 作为 `float`/`double` 存储，通过 float-to-int 转换得到格子体积。float 精度下 $2^{24} \approx 1.6\times 10^7$ 个 site 后精度不足。对于典型 $128^4$ 晶格，这仍在 float 精度范围内（$128^4 = 2.68\times 10^8$，略超 float 精度）。应考虑使用 `double` 或 int 参数。

### 4.4 🟢 `cann.einsum` N 操作数路径可简化

**文件**: `pyqcu/cann/__init__.py:86-129`  
**严重程度**: 🟢 轻微

当前 N 操作数实现枚举所有 $2^N$ 组合并分别调用 einsum。对于 4+ 操作数，这会产生 16+ 次 einsum 调用。可通过递归分解 `(a+ib)(c+id) = (ac-bd) + i(ad+bc)` 减少到 $O(N)$ 次 einsum 调用。
