4. Best-supported explanation
-----------------------------
What is proved:
  * The failure is in the CHILD process, not in pytest: the report is
    "ERROR at setup of ..." with `text = ''`, and the parent session
    completed normally (180 passed + 1 error + summary line).
  * It is reproducible on this host under load (1 of 2 batch attempts), and
    it is fast (the child died after a few seconds, not after a 120/300/600 s
    case budget and not after the 1800 s subprocess timeout).
  * It is NOT reproducible when the child is run on its own: 2/2 direct runs
    and 1/1 `--only kupl` runs passed (see section 6 for the rest).

What contention can and cannot explain:
  * FOR: only the loaded batch reproduced it; the box was running 3+ other
    pytest sessions and 2-4 concurrent `pyqcu.test --quick` children.
  * AGAINST: contention, by itself, does not silence the child.  Forcing the
    worst scheduling I could (taskset to 4 CPUs, nice 19, load ~20) produced
    a *well-formed* report with `TIMEOUT` case statuses (d1), which pytest
    reports as a FAILED case-status/exit-code test, not as a setup ERROR with
    empty stdout.  To produce the observed ERROR, contention would have to
    KILL the child - which contention does not normally do on a box with
    32 GiB of free swap and ~10 GiB of free RAM (no oom-kill in dmesg).

Therefore the most likely shape of the bug is: an abrupt termination of the
child that is invisible to the test by construction.  Ranked:
  (1) A native abort or crash inside the child.  The KUPL path turns every
      C++ exception into `PYQCU::KUPL::<module>: <message>` + MPI_Abort(...,2)
      or std::abort() (lattice_cpu.cpp:885-899); MPI_Abort with exit code 2
      would have hit the fixture's `returncode == 2` branch, but std::abort()
      (SIGABRT) or a segfault inside libqcu/libmpi/libgomp/UCX would not, and
      neither leaves a message on any stream the test keeps.  This is the
      only class of failure that is *inherently* invisible here.
  (2) A crash in the torch/CUDA half of the matrix (14 of 19 cases;
      torch/mg/legacy and torch/mg/strict dominate; the cuda/* cases really
      do create a CUDA context on this host, and dmesg is full of
      `misc dxg: dxgkio_*: Ioctl failed: -22` from the WSL2 GPU driver).
      The absence of a "segfault at" record weakens this.
  (3) An uncaught Python exception in the child (rc=1) - trivially consistent
      with the symptom, and it would be written, with a traceback, to the
      stderr the test discards.
  (4) An external kill: another agent's cleanup (`pkill`, `timeout`, task
      cancellation) hitting the child.  Worth stating because several agents
      were running `timeout ... python3 -m pytest` on the SAME tree at the
      same time, and one of those sessions disappeared mid-run at ~12:27
      (its log ends without an EXIT= line).  SIGTERM/SIGKILL leaves no dmesg
      record and no stdout.

Evidence FOR a genuine native-memory bug (not just contention):
  * the failure is silent and fast - nothing in the child's *observable*
    output (stdout) exists, so no Python-level failure had a chance to be
    reported;
  * the KUPL path passes raw tensor addresses straight into C++ with shape
    validation only in Python (kupl_qcu.py:1352-1360) and a registry keyed by
    the *address* of the set_ptrs tensor (lattice_cpu.cpp:864-880), so a
    lifetime/aliasing mistake would be timing-sensitive in exactly this way;
  * the failure appeared while 3-4 processes were each driving that library
    with their own OpenMP teams and their own MPI/UCX initialisation.
Evidence AGAINST:
  * every direct reproduction attempt of the native path passed (kupl cases
    in ~16 s, 5/5 cases PASS);
  * no segfault record in the kernel log for the one event that did happen;
  * the child that died lived only a few seconds - earlier than the first
    `applyInitQcu` in the sequence (case 10), so it may not have touched
    libqcu at all;
  * the event coincided with a period in which the tree itself was being
    rewritten by other agents.

5. The smallest experiment that would settle it
-----------------------------------------------
Make the child's death observable, then reproduce once.  In order of cost:

  (i) Zero new code, ~1 minute:
      $ for i in $(seq 1 40); do
          PYTHONPATH=$PWD PYTHONFAULTHANDLER=1 python3 -B -m pyqcu.test \
              --quick --json - >/dev/null 2>child.$i.err
          echo "run=$i rc=$?"; [ $? -ne 0 ] && break
        done
      run while the box is loaded by 2-3 other pytest sessions.
      rc alone splits the space: -11 SIGSEGV, -6 SIGABRT (read child.err for
      the `PYQCU::KUPL::` or CUDA line and for the last completed case),
      -9 external/OOM, 1 Python traceback (names the case), -15 external kill.

  (ii) One-line diagnostic (NOT a fix, and not a way to hide the failure):
      in pyqcu/testing/python/test_pyqcu_test_port.py:145 add
      `completed.returncode` and `completed.stderr[-4000:]` to the failure
      message.  Then the batch itself reports the signal and the native
      message, permanently - this is the change that would have answered the
      question the first time it happened.

  (iii) To get the C frame, the host needs either gdb (`gdb --batch -ex run
      -ex bt --args python3 -m pyqcu.test --quick --json -`, with the case
      pinned by `--only <tag>`), or core dumps (`ulimit -c unlimited` + a
      core_pattern that writes somewhere writable).  With `-X faulthandler`
      alone one gets only the Python frame (which case, which ctypes call);
      that is enough to pick the C++ entry point, not enough to name the C
      line.

      by itself produce the symptom.
  So no neighbour test is *required*; what the batch adds over "the test
  alone" is load and duration, not state.

6.7 Bottom line for a release claim
  Do not ship a "contention explains it" sentence yet.  What can be said
  honestly is: the port fixture treats ANY silent non-zero exit of
  `pyqcu.test --quick` as "no JSON report found on stdout", so the current
  evidence cannot distinguish a native crash from a Python exception or an
  external kill, and the one reproduced event left no kernel record.  Two
  cheap changes make the next occurrence self-diagnosing:
    (1) include `completed.returncode` and `completed.stderr[-4000:]` in the
        message at pyqcu/testing/python/test_pyqcu_test_port.py:145;
    (2) in the child, wrap `main()` so an uncaught exception still prints the
        partial report (pyqcu/test/__main__.py:516-542), or at minimum flush
        a "case <tag> starting" line to stderr (the per-case `on_result`
        lines at __main__.py:1715-1720 already do this for completed cases,
        which is how the last completed case was identified in 6.3).
