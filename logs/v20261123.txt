11. CORRECTION 17:25: my MPI gate probe was buggy; the "4-rank hang" is invalid
    Stage probe 2232373 (1 node, correct typed buffers) shows:
      ranks=2: barrier, allgather, allreduce-small, allreduce-large,
               sendrecv-ring, sendrecv-small -> STAGE_OK rc=0
      ranks=4: init, processor, barrier, allgather-ok n=4,
               allreduce-small, allreduce-large -> then timeout rc=137 at
               the next stage, which is sendrecv-ring.
    Root cause of that timeout is the probe, not the fabric:
      sh/mpi_probe.py and sh/mpi_stage_probe.py used peer=(rank+1)%size and
      then comm.Sendrecv(dest=peer, source=peer). Rank i sends to i+1 but
      waits for a message from i+1, while i+1 sends to i+2. That is a
      one-way ring and deadlocks for size >= 3; it only matches at size == 2.
    Therefore:
      - "2 rank OK, >=4 rank hangs" is an artifact of my probe.
      - All fabric-gate verdicts built on this probe (2231089 partially,
        2231110, 2231484, 2231614, 2231906, 2232027, 2232271) are INVALID
        as fabric evidence and must not be cited as such.
      - The rankfile probe 2232208 used the same broken Sendrecv, so its
        2/4/8 rc values are equally invalid, and the earlier note "with a
        rankfile even 2 ranks failed" was measuring nothing.
    Correct ring: send to (rank+1)%size, receive from (rank-1+size)%size.
    Still-standing independent evidence of a real problem: the actual PyQCU
    jobs 2230693 / 2230694 / 2230474 aborted with UCX ud_ep.c:287 unhandled
    timeout inside PyQCU's own collectives, and 2-rank Allreduce worked in
    the same window, so those failures are not explained by this probe bug.
    Next: fix the probe, re-gate, and only then decide whether the fabric is
    actually degraded.

62. Real scaling defect found while watching the L64 case phase
    Each rank reads the WHOLE gauge file, not its slab:

      pyqcu/test/native.py:1434
        array = np.ascontiguousarray(io.load_gauge(path))
        ...
        full = _rank_block(global_full, geometry, compact=False, rank=rank)

    `io.load_gauge` returns the complete global array (`pyqcu/test/io.py:935`),
    and `_rank_block` slices the rank's block out of it afterwards. So an
    N-rank run performs N x the file size of I/O and holds N x the file size
    of RSS before the slice.

    Observed on job 2236885 (L64x128 c64, 128 ranks, 16 nodes):
      gauge file            9,663,682,560 B
      RSS per node          76-78 GB  ->  ~9.5 GB per rank  (>= the file size)
      redundant I/O         128 x 9.66 GB = 1.24 TB
      case phase            > 900 s and still running, cpu ~745%, stime >> utime

    The L48 numbers fit the same model: 3.06 GB gauge x 32 ranks = 98 GB,
    case 377 s.

    This is the same antipattern AGENTS.md already records for the QUDA
    comparison benchmark, where `_load_h5_local_array` uses h5py mpio to read
    only the rank slab. `pyqcu.test` never got that treatment.

    Consequence for task 2: L64 works but wastes ~1.24 TB of reads and ~9.5 GB
    RSS per rank; L128 would need ~4x that in both, which is why "L64-128 at
    scale" is not practically solved even though the numerics are fine.

    Fix (not applied yet, would change the shipped pyqcu.test path):
      read the rank's hyperslab directly from the HDF5 file - the gauge layout
      puts the four spatial axes last, so the slab is a simple 4-D selection -
      and keep the full read only for the single-rank reference path. That
      drops per-rank I/O to 75 MB and per-rank RSS to the slab size.
    A correctness test must pin the slab read against the current
    read-then-slice result bit-for-bit before the old path is removed.
