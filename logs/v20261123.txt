11. CORRECTION 17:25: my MPI gate probe was buggy; the "4-rank hang" is invalid
    Stage probe 2232373 (1 node, correct typed buffers) shows:
      ranks=2: barrier, allgather, allreduce-small, allreduce-large,
               sendrecv-ring, sendrecv-small -> STAGE_OK rc=0
      ranks=4: init, processor, barrier, allgather-ok n=4,
               allreduce-small, allreduce-large -> then timeout rc=137 at
               the next stage, which is sendrecv-ring.
    Root cause of that timeout is the probe, not the fabric:
      sh/mpi_probe.py and sh/mpi_stage_probe.py used peer=(rank+1)%size and
      then comm.Sendrecv(dest=peer, source=peer). Rank i sends to i+1 but
      waits for a message from i+1, while i+1 sends to i+2. That is a
      one-way ring and deadlocks for size >= 3; it only matches at size == 2.
    Therefore:
      - "2 rank OK, >=4 rank hangs" is an artifact of my probe.
      - All fabric-gate verdicts built on this probe (2231089 partially,
        2231110, 2231484, 2231614, 2231906, 2232027, 2232271) are INVALID
        as fabric evidence and must not be cited as such.
      - The rankfile probe 2232208 used the same broken Sendrecv, so its
        2/4/8 rc values are equally invalid, and the earlier note "with a
        rankfile even 2 ranks failed" was measuring nothing.
    Correct ring: send to (rank+1)%size, receive from (rank-1+size)%size.
    Still-standing independent evidence of a real problem: the actual PyQCU
    jobs 2230693 / 2230694 / 2230474 aborted with UCX ud_ep.c:287 unhandled
    timeout inside PyQCU's own collectives, and 2-rank Allreduce worked in
    the same window, so those failures are not explained by this probe bug.
    Next: fix the probe, re-gate, and only then decide whether the fabric is
    actually degraded.

62. Real scaling defect found while watching the L64 case phase
    Each rank reads the WHOLE gauge file, not its slab:

      pyqcu/test/native.py:1434
        array = np.ascontiguousarray(io.load_gauge(path))
        ...
        full = _rank_block(global_full, geometry, compact=False, rank=rank)

    `io.load_gauge` returns the complete global array (`pyqcu/test/io.py:935`),
    and `_rank_block` slices the rank's block out of it afterwards. So an
    N-rank run performs N x the file size of I/O and holds N x the file size
    of RSS before the slice.

    Observed on job 2236885 (L64x128 c64, 128 ranks, 16 nodes):
      gauge file            9,663,682,560 B
      RSS per node          76-78 GB  ->  ~9.5 GB per rank  (>= the file size)
      redundant I/O         128 x 9.66 GB = 1.24 TB
      case phase            > 900 s and still running, cpu ~745%, stime >> utime

    The L48 numbers fit the same model: 3.06 GB gauge x 32 ranks = 98 GB,
    case 377 s.

    This is the same antipattern AGENTS.md already records for the QUDA
    comparison benchmark, where `_load_h5_local_array` uses h5py mpio to read
    only the rank slab. `pyqcu.test` never got that treatment.

    Consequence for task 2: L64 works but wastes ~1.24 TB of reads and ~9.5 GB
    RSS per rank; L128 would need ~4x that in both, which is why "L64-128 at
    scale" is not practically solved even though the numerics are fine.

    Fix (not applied yet, would change the shipped pyqcu.test path):
      read the rank's hyperslab directly from the HDF5 file - the gauge layout
      puts the four spatial axes last, so the slab is a simple 4-D selection -
      and keep the full read only for the single-rank reference path. That
      drops per-rank I/O to 75 MB and per-rank RSS to the slab size.
    A correctness test must pin the slab read against the current
    read-then-slice result bit-for-bit before the old path is removed.

     is essentially orthogonal to the error.  Candidates, in order:
       1 the restrict/prolong pair does not match the fine operator (the
         coarse operator is built from a local stencil patch with
         patch_galerkin_error 3.6e-07, but a 0.36% effect suggests the transfer
         is near-trivial rather than slightly inaccurate);
       2 the correction is applied to a vector other than the fine error (for
         example to x while the residual used for the ratio is computed before
         the update);
       3 damping/acceptance accepts a correction that barely moves the residual.

153. CORRECTION: sections 147-152 are confounded - the interval IS the fine restart
     Review round 1 M2 is right and the consequence is worse than "not decoupled".
     `solve()` chooses the chunk length as
         chunk = min(remaining, correction_interval - since_correction)
     (lattice_clover_multigrid.cpp:488-493) and every `bicgstab_chunk` starts a
     fresh BiCGStab (rhat = r; p = v = 0; rho_old = alpha = omega = 1).  So the
     correction interval and the fine Krylov restart length are the SAME number,
     by construction.  Setting KUPL_MG_CORRECTION_INTERVAL=2 does not "keep
     --restart at 20": it restarts BiCGStab every 2 iterations.

     Two specific claims must be withdrawn:
       - section 149: "The two are now decoupled and the schedule is measured
         with --restart fixed at 20" - they are not decoupled; --restart now only
         sets the DEFAULT interval and the MG enable gate.
       - section 147's table row "restart | 1/5/10/20/50 | confounded" plus
         section 150's statement that "every chunk boundary restarts BiCGStab and
         pays the extra applies" are mutually inconsistent; 150 was right.

     Worse, the A arm is confounded too, and this affects the headline result.
     `A_nomg` used --mg-levels 1, which sets corrections_enabled = false and
     therefore chunk = remaining: that arm ran ONE unbroken BiCGStab, with no
     restart at 20 at all.  B and C ran restarted BiCGStab (every 20 and every 2).
     So 4.647 s vs 6.504 s vs 7.947 s compares three different KRYLOV STRATEGIES,
     not "MG off vs MG on":
       A = unrestarted BiCGStab;
       B = BiCGStab restarted every 20 + 1 correction;
       C = BiCGStab restarted every 2  + 8 corrections.

     What still stands: at every restart/interval setting tried, enabling the
     correction costs more than it saves, and `level0` never falls below the 18
     iterations the restarted runs need anyway.  What does NOT stand is the
     specific 1.40x/1.71x attribution to MG - part of that gap is the restart
     penalty that MG's schedule forces, and a fair comparison needs a plain
     BiCGStab restarted at the same 20 and at 2, with corrections disabled.
     That is the measurement to run next, and no performance claim should be
     quoted until it exists.

     Note the size of the prize: if restarted-every-2 BiCGStab alone is slower
     than 4.647 s by a similar margin, MG's own contribution is small or
     negative but the "1.71x" figure is an artefact of the schedule, not of the
     multigrid.

162. CUDA reference comparison (bg-32): same algorithm, and it would also lose
     Compared cpp/cuda/qcu/src/multigrid.cu + include/lattice_clover_multigrid.h
     (the algorithm; apply_clover_multigrid.cu is only a 165-line shim) against
     cpp/kupl/qcu/src/lattice_clover_multigrid.cpp, line by line at the
     fine<->coarse interface.

     SAME ON BOTH SIDES:
       - One coarse correction from the fine level, then resume fine Krylov; no
         level-0 post-smoothing. The pre/correct/post V-cycle body is dead code
         at two levels on BOTH sides (CUDA MG.h:4008-4029 is only reached for
         lev < num_levels-1; KUPL :1093-1111 likewise).
       - The same explicit 33-tensor Galerkin stencil, the same four assets, the
         same BiCGStab coarse solver, the same argv tolerance slot.
       - The same "accept only if the residual improved, else roll back and
         disable corrections for the rest of the solve" gate.

     DIVERGENT, and both are COST not ALGORITHM:
       1. CUDA keeps a separate `count_restart` counter for the correction
          interval (MG.h:4913/4945/5060/5122) and never chunks the fine loop;
          KUPL's interval IS the chunk length, hence the restart length. This is
          the confound of section 153, confirmed at source level.
       2. CUDA's coarse Krylov runs inside one cooperative kernel with in-kernel
          grid.sync() reductions (multigrid.cu:1833-2090) or graph-replayed
          8-iteration segments (MG.h:795-803, GRAPH_SEG=8 at :778); KUPL runs it
          on the host with 5-6 blocking MPI_Allreduce per iteration, i.e. 150-300
          per correction. That is where ALL of KUPL's 2.3-fine-apply cost lives
          (2.3 measured - 1.0 mandatory damping apply = 1.3).

     AND KUPL IS BETTER ON QUALITY: CUDA takes plain t=1 (MG.h:5089-5090) while
     KUPL takes the exactly optimal analytic damping (:1543-1558). So a CUDA-style
     correction removes LESS per correction than KUPL's.

     THE ALGEBRA THAT SETTLES IT.  A damped additive correction multiplies the
     residual by reduction_bound = sqrt(1 - E/(e*block)), so one correction
     removes 1 - sqrt(1 - E/(e*block)):
         E=2  block=16   cb 0.1020621  red 0.9947780  removes 0.52%  -> 86 corrections = 1 fine iteration
         E=4  block=16   cb 0.1443376  red 0.9895285  removes 1.05%  -> 43
         E=2  block=32   cb 0.0721688  red 0.9973924  removes 0.26%  -> 173
         E=16 block=16   cb 0.2886751  red 0.9574271  removes 4.26%  -> 11
         E=32 block=16   cb 0.4082483  red 0.9128709  removes 8.71%  ->  5
     (these reproduce 0.1020621/0.9947780, 0.1443376/0.9895285 and
     0.0721688/0.9973924 - the measured values - so the formula is confirmed a
     third time.)  One fine BiCGStab iteration removes ~45%.  At E=2/block16 a
     correction must therefore be run 86 times to equal one fine iteration, and
     each correction costs at least one fine apply, so it loses by ~86x.  Even a
     FREE correction would only break even at 86 of them.

     To break even in ONE correction the coarse space must capture ~45% of the
     residual, which needs E/(e*block) ~ 0.7, i.e. E ~ 134 for block=16, e=12 -
     essentially the whole fine space, i.e. no coarsening.  That is the structural
     reason no schedule, damping, interval or cost optimisation can make this
     design win: the bound is about DIMENSION, and it applies to a residual that
     fills the block.  Real multigrid escapes it only because a SMOOTHED residual
     lies almost entirely inside a few coarse vectors - and the measured
     `best_ratio` 0.991-0.993 after the smoothing prefix says our smoothing does
     not concentrate the residual enough for that to happen.

     HONEST STATUS OF THE ORIGINAL REQUIREMENT ("until kupl-qcu-mg has a
     significant speedup"): not achieved, and now not merely unachieved but
     bounded.  Two levers remain, both named by the comparison and neither
     sufficient:
       - hoist the per-iteration global reductions out of bicgstab_chunk (the
         CUDA device-resident coarse solve). Buys at most ~2x; the deficit is 86x.
       - make the residual actually smooth before correcting (a real V-cycle with
         post-smoothing sweeps at level 0, which NEITHER implementation does at two
         levels). This is the only change that attacks the 86x bound rather than
         the cost, and it is a redesign with no measurement yet - it must not be
         claimed as a fix.

173. First real measurement of old-vs-new basis: both are orthonormal, they differ
     ONLY in direction (overlap 0.115), and neither is degenerate
     Ran the Gram analysis bg-43 designed as "step 0: basis only, no cluster, no
     operator" on the two caches actually built at [8,8,8,16] (dof [12,2],
     mg_grid 2 2 2 2, E=2, e=12, block=16, 256 coarse sites; lonv is
     (2,12,4,2,4,2,4,2,4,2)):

       tag  nv_builder             |G-I|max   cols/E  cond_med  rank  frac(|G-I|<1e-3)
       inv  inverse-iteration/2    9.54e-07   1.0000   1.0e+00    2      1.000
       leg  legacy-residual/1      1.01e-06   1.0000   1.0e+00    2      1.000

     So the historical loop does NOT produce a degenerate or zero basis: after its
     final normalisation it stores two ORTHONORMAL vectors per coarse block, full
     rank, condition number 1.  That is exactly what white noise looks like in a
     192-dimensional space, and it is why every Gram-based quality test passes for
     both - including the builder's own G=I assertion, which therefore cannot
     tell the two builders apart.

     The difference is direction, and it is large:

       cross-basis overlap per site ||A_new^H A_old||_F / (||A_new|| ||A_old||):
         mean 0.1151   median 0.1124   max 0.1902
       column-norm ratio leg/inv: median 1.0000

     An overlap of 0.11 where 1.0 means "the same subspace" says the two bases span
     almost disjoint planes in each block, at identical column norms.  They are not
     two versions of the same object - they are two different objects.

     Capacity is identical by construction and confirms the algebra a fourth time:
       capture = E/(e*block) = 2/(12*16) = 0.010417
       sqrt(capture) = 0.102062   (= the capture_bound this log has quoted)
     So neither basis can capture more than ~1.04% of a residual that fills the
     block; the bases can only differ in how much of a SMOOTHED residual they
     capture, which is the one question Gram analysis cannot answer because it
     involves no residual at all.

     What this settles and what it does not:
       - settled: the old builder is not broken in the sense of producing a
         rank-deficient or unnormalised basis; it produces well-formed noise.  That
         vindicates the "white noise" description of section 167/171 and it kills
         the hypothesis that the old basis was degenerate.
       - not settled: which basis captures more of an actual smoothed residual.
         That needs one residual vector, i.e. the residual dump of bg-43's design or
         its zero-rebuild fallback (k Krylov iterations in torch with the reference
         operator).  No cluster-side change is required for the fallback, and the
         metric then costs zero operator applications per basis, so both bases are
         evaluated on a bit-identical r.

     The two arm caches are preserved at data/nvlog/caches/{inv,leg} plus their
     .json sidecars, so this analysis is re-runnable without rebuilding anything.

177. CORRECTION of section 171/176's mg-3 conclusion: 3 levels need PLUMBING, not
     physics, and no coarse gauge is involved anywhere
     I told the operator that mg-3 "cannot be built" and "needs physics code -
     a coarse gauge and coarse Clover construction".  Both parts were wrong, and
     `bg-41` disproved them with code and a numerical check.

     WHAT I GOT WRONG AND WHY: I read the two C++ builders' signatures
     (`applyMultigridBuildNullVectorsQcu` / `applyMultigridBuildStencilLocalQcu`
     take gauge + Clover) and inferred that a level-2 operator must therefore be
     produced from a coarse gauge.  I never read the torch/CUDA chain's recursion,
     which defines the hierarchy completely differently.

     THE ACTUAL RECURSION (no gauge anywhere):
         op(0) = fine odd-Schur Clover operator
         op(L) = R_L · op(L-1) · P_L
     i.e. each coarse operator is the Galerkin projection of the PREVIOUS
     operator, where the previous operator may itself be a 33-tensor stencil.
     `pyqcu/cuda/_multi_gpu.py:229` says it in one line - `S = lambda v:
     apply_stencil(hnn, hdg, sit, v)` - and that is the whole handoff.  A
     tree-wide search for `coarse_gauge`/`block_average`/`coarsen_gauge`/
     `coarse_clover` finds NO implementation: the construction I said was missing
     does not exist because it is not needed.

     THE STENCIL IS BUILT BY PROBING, AND PROBING WORKS ON A STENCIL PARENT:
       - null vectors: `give_null_vecs(matvec=apply_stencil(parent_stencil))`
       - projection:   `build_stencil(parent_matvec, ...)` - takes ANY matvec
     Both primitives are generic in `(E, e, dims)` and already used by the torch
     chain (`pyqcu/torch/tools/_multigrid.py:105-166`, `:168-241`, `:873-953`).
     Verified numerically this session on synthetic parent stencils:
         isotropic block 2, E=(2,2): max ||A2 v - R A1 P v||/||.|| = 4.89e-16
         support of A2·delta        : exactly 33 offsets (the 33-point gallery)
         anisotropic (2,2,2,1), E=(3,3): 4.26e-16, 33 offsets
     so a 33-tensor parent can only produce couplings at {0, ±e_mu, ±e_mu±e_nu},
     i.e. the construction is inductively valid to any depth.

     WHAT IS GENUINELY IMPOSSIBLE (and must not be attempted): handing a coarse
     gauge + coarse Clover to the two C++ builders.  Wilson-Clover is onsite plus
     1-hop; a 33-point stencil carries 2-hop couplings, so NO gauge reproduces it
     and the builders would silently build the hierarchy of a different operator.
     That is the real constraint - it says the level-2 build must happen in
     PYTHON/torch, where a matvec is an argument, not that mg-3 is impossible.

     WHY THE SOLVER IS NOT THE PROBLEM EITHER: `lattice_clover_multigrid.cpp:312`
     accepts 1..5 levels, `:392-435` reads the per-level E/dims/pointer quartet,
     `:975-978` applies `multigrid_coarse_dslash_wide` with no gauge parameter at
     all, and `:986-1001` pass `c.E, p.E` and both dims into generic restrict/
     prolong.  `pyqcu/test/native.py::_configure_legacy_mg` is already N-level
     (`for level in range(1, depth)`), and `worker.py:203-259` already loads one
     root per level.  `--mg-levels 3` is refused by ONE gate
     (`native.py:4121-4136`) and the builder is the only 2-level component.
